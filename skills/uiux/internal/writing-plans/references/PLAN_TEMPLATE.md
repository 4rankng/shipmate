# Feature Implementation Plan

Optional expanded template for higher-risk changes. Omit inapplicable sections; a small fix may
use one compact task with files, AC evidence and risk instead. Keep this artifact machine-local
unless repository policy or the user requires a committed design document. Follow
[workflow-policy](../../workflow-policy.md); this template creates no additional approval gates.

One plan per requirement: keep revisions append-only in the same file (revision history below),
never spin a second plan file. Task numbers are stable IDs — never renumber across revisions;
reviewers and executors cite them.

Each task is one action with a checkable result, sized so its `Verify:` line proves it done. A
task without a `Verify:` line carrying an exact command and its expected result is incomplete;
prose assertions do not count. Record the change shape — exact file paths, signatures, test
assertions and the requirement's values — not full implementation bodies; a body belongs here
only where the interface alone cannot determine the algorithm.

Mark a task title with `[P]` when it is parallel-safe: it touches no file another in-flight task
touches and depends only on completed tasks. Independent `[P]` tasks may run as one concurrent
wave in isolated worktrees; waves run sequentially. A task without the marker runs alone. Add
`Depends on: Task N` only when the dependency is not the immediately preceding task.

## Acceptance-criterion traceability

Every task traces to at least one AC (or is named as an enabling step with its owner); every
uncovered AC is explicitly in non-goals. A plan that silently drops a criterion is incomplete.

| AC | Current requirement and source | Planned file/interface | Plan task | Fail-before evidence | Pass-after evidence |

## Risks and rollback

For higher-risk work, name each top risk's first detection signal — a failing test, a log line,
a metric threshold — so execution and review can tell "not yet failed" from "not detected".

## Revision history

Append one line per material revision: date, what changed, whether affected review was

## Plan-review handoff

The controller records the current plan path, review cycle, and review records outside this file.
Do not edit this file merely to track task progress. Formatting-only edits continue; material clear
changes receive fresh plan reviews before implementation continues. The requirement digest and
plan status above are the freshness anchors: consumers compare the digest before adopting the
plan, and never patch a stale plan — they escalate back to planning.
